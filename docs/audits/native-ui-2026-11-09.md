## NumberFlow: avoid rendering-driven updates

- **Android defect:** committing the last displayed value wrote Compose snapshot state after a value update. That could schedule another composition and change a decreasing transition's direction when the values became equal.
- **Fix:** retain primitive, non-observable history for the mounted component. Commit through SideEffect, cache the chosen direction for each value, and preserve it on unrelated parent updates.
- **Android preparation:** remember the formatted output by value and formatter configuration. Resolve decimal glyphs only when locale changes. Typography and animation remain native Compose.
- **iOS defect:** previous-value tracking and glyph preparation used several observable state properties. Formatting and token construction repeated whenever the body evaluated; token construction also allocated a positional dictionary.
- **Fix:** one lazily initialized, main-actor StateObject owns non-publishing memoization. Cache presentation by numeric value, format, currency, precision, and locale; retain token storage when the formatted string stays the same. Build tokens with a reserved array and scalar digit position.
- **Correctness:** committed history does not publish changes. Every glyph table has ten entries even if Foundation fails to format a digit. The public API, accessibility value, and OS locale formatting remain unchanged.

Both AOT and DevRuntime invoke these same platform primitives. Release output contains direct native calls, not a NumberFlow interpreter.

## FastList: remove observation allocations

- **Android AOT defect:** each leading-visible-row observation filtered the platform's visible-items collection into a new list before selecting a row.
- **DevRuntime defect:** its separate selection algorithm used nullable integer accumulators. It also duplicated the AOT behavior in another implementation.
- **Fix:** one typed inline helper for AOT and DevRuntime. Scalar indexes and indexed loops avoid filtered collections, iterators, nullable primitive accumulators, and per-item geometry adapters.
- **Preserved semantics:** only items intersecting the viewport count. Sticky headers obscure covered rows; reverse layouts select the visual leading item; empty or fully obscured collections keep the original fallback behavior. List, grid, and masonry callers supply typed geometry accessors.
- **Work bound:** the helper examines only platform-visible items, with a header pass when needed. It never materializes the full source collection.

## Keyed iOS rows stay lazy

Generating the current component-parity app exposed an additional AOT list issue. When a Swift
`FastList` used a key together with swipe or reorder actions, generated `body` code mapped every
source index into a new `NexaIdentifiedListRow` array and boxed each key as `AnyHashable`. The
native list later displayed rows lazily, but the identity array had already done O(N) work and
allocated O(N) wrappers on every parent refresh. Android's `LazyColumn` passed its key expression
directly to the lazy item provider.

The Swift backend now emits a typed `RandomAccessCollection` whose row and ID are produced from an
index when requested. This removes Nexa's eager full-list mapping and key boxing while preserving
stable item identity, reorder behavior, and lazy row content. Sectioned native lists use the same
collection per section. Regression checks inspect generated AOT source and reject the previous
full-list mapping.

The generated component-parity AOT source also passed a static hot-path scan: the iOS app contains
no `AnyView`; Android uses `LazyColumn` item providers; numeric Compose state uses specialized
primitive state holders, with no generic numeric `mutableStateOf` declarations. This source scan
does not replace interaction profiling.

The current parity app passed `nexa audit examples/component-parity/App.nx
--target all --release-sizes`. Both AOT Release targets compiled successfully:
iOS executable 9,029,784 bytes; Android APK 2,942,841 bytes and AAB 6,297,176
bytes, with R8 and resource shrinking enabled. The [full audit report](native-ui-2026-11-10/component-parity-release.json)
records the build settings and source sizes. This is build evidence, not a

## Generated parity app: high-risk runtime paths

The full examples/component-parity/App.nx AOT output was inspected on both
platforms and compiled as a Release iOS app and a Debug Android app. This pass
found two high-risk response-memory paths and one generated Swift compile defect.

| Finding | Generated-code behavior | Fix and evidence |
|---|---|---|
| iOS response limit applied after full buffering | URLSession.data(for:) and remote-image data(from:) retained the complete body before checking the configured 64 MiB limit. ImageIO thumbnail work could also occur lazily on the SwiftUI task/render path. | Shared URLSession delegate rejects advertised lengths and cancels when the next chunk would exceed the limit. ImageIO thumbnail decode runs in a cancellable utility task and caches pixels immediately. Downloads now stream into a same-directory staging file, reject advertised or incoming sizes over the limit, and remove partial files on cancellation or failure. The native fixture's 4 KiB budget capped both memory accumulation and download file writes at 4 KiB; an unknown-length 64 KiB response was canceled after 5 KiB delivered. A declared oversized body was rejected before accumulation. Three image fixtures preserved geometry and pixel hashes, invalid data remained rejected, and the main actor progressed during a large decode. |
| Android image response copied through multiple full-size buffers | The generated Cronet image adapter staged bytes in ByteArrayOutputStream, copied them to ByteArray, then copied them into Coil's Okio Buffer. | The image path now writes each Cronet ByteBuffer directly into the Buffer consumed by Coil. It rejects an oversized advertised Content-Length before reading and clears failed/canceled buffers. The generated Android Release Kotlin and Debug APK compile; a backend regression asserts the image path contains no intermediate byte-array conversion. |
| Android generic network transport allocated a byte array for every Cronet chunk and copied the completed body again | `Network.fetch` and `Network.download` copied each direct 32 KiB Cronet buffer into a fresh `ByteArray`. `ByteArrayOutputStream.toByteArray()` then copied the complete response at completion. The size expression could overflow for a large caller-supplied limit. | The generated transport reuses one transfer array, caps accumulator capacity at the configured limit, transfers ownership without a final full-body copy when the accumulator is exact-sized, rejects known oversized responses before reading, and uses subtraction-based bounds checks. Downloads serialize close with asynchronous file writes so cancellation cannot race a pending write. Backend checks verify the emitted source; generated fetch/upload/download hosts are compiled on both platforms. |
| iOS parity AOT failed to compile on tabs and list layouts | Index aliases duplicated switch patterns when tab index equaled position; deep-link code emitted an unused query local for parameterless routes. Swift 6 also found UIKit-backed item measurement and grid layout construction outside the main actor. | Generated tab aliases are deduplicated, query parsing is emitted only for parameterized routes, and UIKit layout helpers are main-actor isolated. The entire generated parity app now builds for the iOS simulator in Release with Swift warnings treated as errors. |

The image and network regressions run in
cargo test -p nexa-cli --test native_ui_hotpaths. Native fixtures use an iOS
simulator and private URLProtocol responses; they do not capture screenshots.
The Swift download fixture verifies declared and unknown-length rejection,
exact byte caps in staging files, exact-limit and empty downloads, cancellation,
file cleanup, and no remaining pending delegate entries.
The Android Debug APK and Release Kotlin sources compile. Release packaging
could not run because the generated project has no Android signing storeFile.

These checks establish bounded accumulation and removal of avoidable copies;
they do not establish application frame rate, battery life, or absence of all
OOMs. The public `Network.fetch` result intentionally owns its complete body,
up to the configured response limit, because its API returns a `Data` or
`ByteArray`; callers handling large files should use `Network.download`.
