# Nexa Plugin Development

Help extend Nexa with optional features that users can install without placing every integration in the core framework. Read `plan.md`'s plugin-system and platform-implementation sections and inspect the current repository before proposing interfaces. The package manager and install workflow are roadmap items unless present in code; never imply they already work.

## Boundaries

- Keep the default Nexa compiler and core component set usable without optional plugins or their native dependencies.
- Give each plugin a clear public API, platform implementations, dependency declarations, and generated bindings where the current architecture supports them. Keep platform-specific code isolated by platform and plugin.
- Reuse the generated core network/path/file bindings for transport and storage-adjacent plugin work. Network plugins should call URLSession on iOS and Cronet on Android, preserve typed request options, and avoid introducing OkHttp, a second image loader, JSON/RPC, or a runtime service locator.
- Core value types available to typed plugin APIs include scalars, `Array<T>`, `Set<T>`, `Map<K, V>`, `Pair<A, B>`, and `Triple<A, B, C>`. Set elements and map keys are limited to scalar `String`, `Bool`, or numeric types. Arrays, sets, and maps support compile-time checked lookup, membership, direct action mutation, and native iteration; inline `map`/`filter`/`reduce` closures are available for `Array<T>`. Plugin IDL methods should still keep collection shapes explicit and avoid claiming generic or reference-type behavior that the core language does not support.
- Prefer statically typed interfaces and generated direct calls. Native class methods support named arguments and `Void` action calls; avoid JSON/RPC, string-based dispatch, reflection, dynamic dictionaries, and per-frame boundary crossings.
- Declare scalar compile-time options in `native.nxid`; users set them under `plugins { Namespace { ... } }` in the generated `nexa.config.nx`. Validate required, optional, defaulted, and typed values before generation and expose them as direct native constants rather than a runtime dictionary.
- Do not put plugin-specific behavior in the parser, common UI nodes, or both backends unless it is truly part of the shared language contract.
- Do not implement SQLite, MMKV, maps, or another example integration merely because it appears in the roadmap. First establish the plugin-system capability or implement only the integration the user requested.
- The supported workflow is `nexa plugin init <plugin.id> --out <directory> --name <TypeName>`, followed by `nexa plugin check <plugin-directory|native.nxid>` and `nexa plugin generate <plugin-directory|native.nxid> --target <swift|kotlin|cpp>`. Pass `--package` for the generated Kotlin package; the C++ target emits a typed contract header. The scaffold includes `plugin.config.nx` and `native.nxid`; the manifest parser validates package identity, schema, source paths, platform metadata, native dependency coordinates, iOS usage descriptions and string/boolean/string-array entitlements, Android permissions, and assets. The native parser validates structs, enums, typed error variants and payloads, services, interfaces, native classes/components, properties, events, methods, field types/defaults, recursive value layouts, generic arity, compile-time options, and asynchronous throwing boundaries; layout-less opaque `type Name` declarations are unsupported. Binding generation emits direct Swift protocols/types, Kotlin interfaces/types, optional C++ value/error/service/class contracts, native component wrappers, private compile-time conformance checks, and Kotlin factory probes for native classes. Swift errors use associated-value `Error` enums; Kotlin errors use sealed `Exception` subclasses and `@Throws` metadata. A local `.nx` app can declare `plugin "path" as Namespace` and call `await Namespace.method(...)`; async throwing calls require explicit `try { ... } catch { ... }` recovery. Typed catch cases match declared error variants and bind payloads; an else arm handles untyped or remaining failures. Native class constructors and instance method calls lower to direct object calls, while service calls retain their stateless contract. Qualified visual components use `Namespace.Component(...)` and lower to a direct SwiftUI/Compose wrapper call. A package may combine Nexa source and a native contract; generated projects honor source globs and platform minimums, declare Swift packages and Maven coordinates in Xcode/Gradle, and place generated contracts in the host project. Kotlin implementation files must currently share one package per plugin. Native-class events support instance-scoped `.event { ... }` action handlers with typed payloads. Native component events use `.onEvent { ... }` modifiers attached to qualified component calls and become direct callback arguments to the generated wrapper. The compiler validates synchronous disposal declarations, tracks direct immutable aliases within each action sequence, and catches repeated disposal or later uses; it does not yet reason about ordering across separate callbacks. Native project toolchains fetch declared packages; privacy manifests, extended host metadata, plugin installation, precise identity propagation through navigation and component scopes remain future work. Optional C++ host adapters support synchronous and non-throwing async scalar, optional scalar, string, and byte methods plus async typed errors with non-optional primitive, string, or byte payloads on both platforms. Async collection parameters and returns use the existing platform adapters for supported shapes and run conversion on the background async path. C++ event adapters and broader collection combinations remain future work.
- Plugin manifests may declare iOS `linkerFlags` as a list of individual linker arguments. Nexa preserves their declaration order and quotes them into Xcode `OTHER_LDFLAGS`; control characters and empty arguments are rejected.
- Use `nexa plugin init <plugin.id> --kind pure` for a source-only package. It creates `plugin.nx` and `assets/`; the app declares the package with the same `plugin "path" as Namespace` form, and the compiler loads reusable components/functions through the normal `.nx` graph. Use the default `--kind native` for IDL-backed Swift/Kotlin integrations. Pure plugins do not create native dependencies or bindings.
- `nexa plugin check` parses the manifest and native IDL, syntax-checks the declared Nexa source/import graph, and confirms declared platform source patterns and asset roots exist. When Xcode and the iOS simulator SDK are available and no SwiftPM dependencies are declared, it type-checks Swift sources against the generated contract; SwiftPM dependencies require generated Xcode resolution. When `kotlinc` is available, it type-checks dependency-free Kotlin service/class sources; external Android imports, Maven dependencies, and Compose components require the generated Gradle build.
- Put plugin-owned images and other platform resources under `assets/`. Project generation copies reachable plugin assets into Android `drawable-nodpi` and an iOS asset catalog, with deterministic names. Keep resource names stable and lowercase-safe because generated Android lookup uses resource identifiers.
- Native scaffolds do not require a hand-authored C ABI. The normal path is direct Swift/Kotlin code generation; `nexa plugin generate --target cpp` emits an optional typed C++ contract, and generated C++ host adapters support synchronous and non-throwing async scalar, string, and byte methods plus async typed errors with primitive, string, and byte payloads on both platforms. Async collection calls use supported platform collection adapters; C++ events and broader collection combinations remain open.
- Treat native bindings as direct typed calls with explicit ownership. Native class bindings expect a concrete `{Name}Impl` implementation and alias `{Name}` to it, keeping construction direct. Do not add reflection, JSON/RPC, a runtime registry, or a manually maintained C wrapper to the normal Swift/Kotlin path.
- Generated Swift native-class contracts are `@MainActor` isolated. Kotlin native methods stay on the caller's coroutine dispatcher; Nexa does not silently switch plugin work to a background dispatcher. Plugin implementations must honor their SDK's threading rules and choose explicit dispatch where needed.
- Expose platform differences intentionally when APIs cannot share the same behavior; do not hide incompatible semantics behind a misleading common abstraction.

## Implementation workflow

1. Determine which pieces exist today: plugin metadata, IDL, dependency resolution, code generation, and Swift/Kotlin binding support.
2. State the smallest vertical slice needed, including how a `.nx` app declares and calls it and how each native backend resolves it. Prefer the existing direct local-plugin path over a registry or runtime lookup.
3. Keep plugin API/schema, platform implementation, and compiler integration in separate maintainable modules.
4. Make generated native bindings typed and direct, with ownership and error behavior made explicit.
5. Document installation, platform setup, supported targets, and current limitations. Do not claim installability until the package/install path exists.
6. Validate the plugin independently and validate a minimal Nexa app that uses it; inspect output for both platforms that the plugin claims to support. Declare implementation files with `ios.sources` and `android.sources` in `plugin.config.nx`; entries may be files, directories, or `*`/`?`/`**` patterns. When omitted, the scaffold fallback is `ios/Sources` and `android/src/main/kotlin`.
