# Nexa Framework Development

Work on the Nexa framework itself: a Rust ahead-of-time compiler that turns `.nx` app source into native SwiftUI or Jetpack Compose code. Read the repository `README.md`, `plan.md`, and the relevant language docs before changing architecture or syntax. Treat the implementation as an early prototype; do not describe roadmap items as implemented.

## Architecture boundaries

- Keep the source pipeline separated into syntax, semantic analysis, platform-independent IR, backend code generation, and CLI responsibilities. Put each responsibility in its existing crate or a focused module under it.
- Keep the authoring surface small: expose one vertical `Column` layout and infer the type of `let` or `state` declarations when a non-empty initializer has one deterministic type. Preserve explicit mutability (`let` is immutable, `state` is mutable); do not infer or rewrite mutability from later use. Integer literals default to `Int32` and decimal literals to `Float64`; component parameters stay explicit. These are compiler-only conveniences and must preserve direct generated native output.
- Keep user value models small and static: top-level `struct Name { field: Type, ... }` declarations resolve to typed IR value structs, positional constructors, and direct Swift/Kotlin value members. Generate each struct once in a dedicated backend module and lower construction directly to its native initializer; do not add reflection, helper registries, boxed field access, named constructor dispatch, methods, inheritance, or recursive value layouts.
- Keep the first function slice pure and statically typed: app-local `fn` declarations have explicit parameter and return types, exactly one return expression, and direct calls. Lower them to private top-level native helpers; do not add a runtime registry, dynamic dispatch, closure boxing, or interpreted call path. Thread function signatures through semantic lowering so `let` and `state` can infer a call's return type with the same deterministic numeric defaults.
- Use `platform ios { ... }` and `platform android { ... }` for target-specific widgets. Pass the selected target through compiler lowering and discard inactive blocks before semantic analysis and backend generation; never model this as a runtime platform condition.
- Run conservative IR optimizations after semantic lowering and before either backend. Fold only pure literal expressions and remove statically unreachable UI/action branches; preserve short-circuit behavior, state semantics, and native component mappings. Keep the optimization pass in `nexa-compiler` so backend code remains platform-focused.
- Keep diagnostics separate from hard errors: report unused states/constants/function parameters/action-loop and `FastList` row bindings/functions/component parameters and provably constant conditions with source spans, and expose a `--deny-warnings` boundary for strict CI or release builds. Treat loop and row binding usage lexically across nested action/node bodies. Remove only declarations proven unreachable from the lowered IR; preserve component signatures and dynamic state behavior.
- Keep the common IR platform-independent. Swift-specific generation belongs in `nexa-backend-swift`; Kotlin/Compose-specific generation belongs in `nexa-backend-kotlin`.
- Keep closed enum declarations in the shared IR. Validate names, duplicate cases, enum-case expressions, and enum-aware `when` branches during semantic lowering; emit private native Swift enums and Kotlin enum classes without registries, reflection, or boxed case values. Defer associated payloads until their exhaustiveness and allocation rules are defined.
- Keep permissions as compile-time project metadata in a separate generated `nexa.config.nx`. Validate names, duplicate entries, and non-empty iOS purpose messages in a focused config parser; let the CLI project generator emit only the required iOS `Info.plist` usage-description keys and Android manifest permissions. Do not support app-level permission declarations, a runtime permission registry, or a fake iOS notification usage key; keep runtime request APIs separate from host metadata.
- Keep compiler/code-generation responsibilities in separate files and focused subfolders. Prefer small modules with clear ownership over a monolithic file, while avoiding abstractions that add indirection without reuse.
- When a project targets both platforms, load and parse the source/import graph once and lower each target independently. Preserve target-specific semantic checks and platform-block pruning; do not share target-specific IR or introduce a runtime abstraction to save compile work.
- Add core default components to Nexa's shared language/IR and both native backends when requested. Optional integrations such as SQLite, MMKV, and maps belong in a future plugin layer; do not add them to core by default.
- Keep the authored app in `.nx`. Generated Swift/Kotlin is compiler output; do not ask app authors to write native code to use supported Nexa features.
- Keep project scaffolding in the CLI's dedicated project module. `nexa generate` may write Xcode and Gradle host files, but templates must remain separate from compiler semantics and backend generators, use feature-gated dependencies, and be deterministic/idempotent so regeneration only changes affected outputs.
- Keep local plugin declarations and calls in the typed frontend. Resolve each declared `interfaces.nxid` at compile time, merge its method signatures into the normal call checker, and lower calls to the existing `Expr::NativeCall` without a plugin registry, reflection, or boxed boundary. Project generation may include conventional plugin source trees (`ios/Sources` and `android/src/main/kotlin`) as native build inputs; package installation and version resolution remain outside this slice.
- Keep plugin configuration typed and compile-time: plugin authors declare scalar options in `interfaces.nxid`; `nexa.config.nx` stores values under the app's plugin namespace, and the CLI validates required/optional/defaulted values before emitting direct Swift/Kotlin constants. Do not add a runtime option map, JSON/RPC boundary, or reflection lookup.
- Keep incremental build caching in the CLI boundary. Fingerprint the complete entry/import/plugin-IDL source graph, include plugin platform source trees and `nexa.config.nx` for project generation, cache generated native source, warning text, or complete host projects under `.nexa/cache`, and restore only on an exact target/schema match. Do not cache target-specific IR in the shared compiler or make cache state part of generated app code; cache misses must follow the normal compiler pipeline.
- Prune unused plugin declarations after function/state/component reachability analysis. Only namespaces referenced by surviving `Expr::NativeCall` nodes may reach project generation; do not copy an unused plugin's platform source tree into the host project.

## Native output and performance

- Generate ordinary native SwiftUI and Kotlin/Jetpack Compose code with direct platform calls and minimal framework machinery. Preserve platform behavior, accessibility, and native state semantics.
- Prioritize predictable allocations and direct native primitives. Make performance claims only when supported by generated output or measurements; do not label the prototype native-equivalent without benchmarks.
- Keep module-wide code-generation scans single-pass and share recursive IR traversal across backends. Derive imports and optional native helpers from analyzed features; never emit broad wildcard imports by default.
- Emit each reachable user component once and call it directly for every use. Do not duplicate its view body at call sites or add a component registry/runtime; keep generated component declarations out of the app's public API.
- Android image nodes must use Coil 3 (`coil3.compose.AsyncImage`) and keep image-specific code isolated in the Kotlin image generator.
- All generated network traffic, including remote images, must use the platform default stack: URLSession with a protocol-aware URLCache on iOS and Play Services Cronet on Android. Configure Android Cronet with a 64 MiB disk cache, HTTP/2, QUIC, and Brotli, initialize `CronetProviderInstaller` in generated remote-network hosts before Compose content starts, and route Coil 3 through a generated Cronet `NetworkClient`; never add an implicit OkHttp fallback for Nexa images. Keep request/download, path, and file helpers in dedicated backend generator modules and emit them only when the lowered module needs networking. Keep the Coil image adapter in a separate feature-gated fragment so network-only apps do not carry image imports or dependencies.
- Remote `Image(url: ...)` URLs are typed `String` expressions. Validate literal absolute HTTPS URLs during semantic lowering and guard dynamic values in the generated URLSession/Coil loader before starting a request; preserve the direct native image path without a shared image runtime.
- Keep the core native library feature gate namespace-based: only `Network`, `Path`, or `File` calls may emit the shared network/file helpers. Typed plugin calls must remain direct and must not pull Cronet, URLSession helpers, or unrelated native code into the generated app.
- Permission declarations stay compile-time project metadata. `Permissions.status(permission: ...)` lowers to a typed asynchronous native status query and emits only the platform frameworks/helper needed by that module; do not add a shared permission registry. Request callbacks and denial recovery remain separate lifecycle work.
- Native network helpers must expose method, body, headers, timeout, cache policy, redirect policy, response byte limits, downloads to a destination path, and optional certificate pinning. Use URLSession async APIs with the current Security trust-chain API and a private Cronet callback client wrapped directly in native coroutines; do not add a shared request registry, JSON bridge, or interpreted runtime.
- Qualified native calls are part of the source language: `Network.fetch`/`download`, `Path.documents`/`caches`/`temporary`/`appSupport`/`join`, and `File.exists`/`readText`/`writeText`/`delete` lower to `Expr::NativeCall` during semantic analysis. Keep argument names and defaults in the compiler, emit direct platform calls, and feature-gate the native helper/imports from the shared IR scan. Until typed Result errors exist, Swift source calls use explicit empty/false fallback expressions for throwing native operations; do not hide failures behind a runtime service locator.
- Theme values belong in typed, platform-independent IR and should resolve statically when possible. Emit system appearance lookups only for apps that use adaptive color tokens; keep typography, spacing, radius, and other token behavior native to each backend.
- User-defined components should lower to typed IR and ordinary native view/composable declarations. Resolve relative `.nx` imports at compile time, preserve component-local state per native instance, reject recursive composition, and prune unreachable generated components; avoid runtime registries and duplicated UI trees.
- Conditions and scalar operators should be type-checked before code generation and lower directly to Swift/Kotlin operators and native control flow. Preserve short-circuit semantics and avoid implicit numeric conversions or an interpreted expression runtime.
- Action blocks may lower `for item in array`, `for item in set`, destructured `for (key, value) in map`, Int32 `for item in start..end`/`start..<end` ranges, and positive literal `step` ranges, plus `while condition`, `break`, and `continue`, directly to native control flow. Validate iterable, map binding, range step, and bound types and loop-only control statements in semantic lowering; keep loop bindings immutable, reject loops in pure functions, and do not introduce an iterator, materialized range array, map entry wrapper, or callback runtime. Use Swift `stride` and Kotlin `step` for stepped ranges and `FastList` for repeated UI rows.
- Scalar and closed-enum `when` branches use a typed scrutinee, unique literal/case values, and a required default. Lower directly to Swift `switch` and Kotlin `when`; do not introduce a runtime case registry. Keep associated-value enum patterns and range cases separate until their exhaustiveness rules are defined.
- Nullable bindings use `Type::Optional`, `null`, a typed `Coalesce` expression, and optional collection indexing. Lower `??` directly to Swift `??` and Kotlin `?:`, and lower `optionalArray?[index]`/`optionalMap?[key]` to native chaining, preserving short-circuit evaluation and avoiding wrapper/runtime allocations. Keep general user-defined safe member access and forced unwraps out until their type and failure semantics are defined.
- Pair/Triple optional members may use the typed `Member` IR with `optional: true`; lower `?.first`/`?.second`/`?.third` directly to Swift/Kotlin optional chaining and preserve the optional field type. Value-struct members use the same path; forced unwraps and reference-type members remain deferred until their type and failure semantics are defined.
- Struct members use the same typed `Member` IR as Pair/Triple. Lower `user.field` and `optionalUser?.field` directly to native member access; keep field names sanitized in backend output and preserve the optional field type without a wrapper runtime.
- String interpolation should lower `$name` and `\(expression)` segments into the shared typed IR and direct Swift/Kotlin interpolation. Reuse normal expression typing, preserve direct native interpolation, and avoid template runtimes or intermediate strings.
- Preserve the core value mappings for `Array<T>`, `Set<T>`, `Map<K, V>`, `Pair<A, B>`, and `Triple<A, B, C>` in the typed IR and both backends. Keep literals type-directed, map duplicate keys last-value-wins, and Set/Map hash keys scalar-only until compatible native constraints are modeled. Use Swift tuples for Pair/Triple and Kotlin standard-library Pair/Triple, without generated helper wrappers; `.first`, `.second`, and `.third` must remain direct tuple/field access. Array indexing accepts an `Int32` index and emits direct native subscripting (`Int(index)` on Swift); map indexing accepts the declared key type and returns `Optional<V>` directly from native lookup. Optional arrays/maps use `?[index]` and native chaining. Scalar membership emits Swift `contains` or dictionary-key lookup and Kotlin `in` directly. Keep array bounds and missing map keys native and do not add a wrapper or runtime lookup layer. Mutation and transformation APIs remain deferred; Set iteration and destructured map iteration remain direct native loops. `FastList` iterates arrays for UI rows. Update the language guide, design decisions, examples, and this skill together when that boundary changes.
- iOS `FastList` should use native `UITableView` virtualization and cell reuse; host SwiftUI row content with `UIHostingConfiguration` instead of routing large lists through SwiftUI `List`. Keep row lookup direct and avoid materializing a second row collection.
- Keep component generation separate by concern (controls, text input, image loading, layout, navigation, lists, keyboard handling, expressions, and shared formatting helpers).
- Keep `Text` on native text rendering. Lower static `fontWeight` (`Normal`, `Medium`, `Semibold`, `Bold`), positive `lineLimit`, non-negative `lineHeight`/`letterSpacing`, and `selectable` directly to SwiftUI modifiers and Compose text APIs; do not add a shared text layout runtime.
- Lower shared layout alignment to native stack constructor arguments; avoid adding wrapper layouts solely to position children. Keep common style-property predicates in the shared IR to prevent backend feature scans from drifting.
- Keep layout borders typed and static. Require `borderColor` and `borderWidth` together, lower Swift to a native `RoundedRectangle` stroke overlay and Android to `Modifier.border`, and feature-gate the Compose border/shape/color imports. Do not introduce a dynamic style map.
- Keep the first animation slice native and static. A layout `animation` spec (`Spring`, `EaseIn`, `EaseOut`, `EaseInOut`, or `Linear`) lowers to SwiftUI animation and Compose `animateContentSize` with native specs; feature-gate its imports and never add a shared frame scheduler or per-frame bridge. Defer transforms, transitions, and gesture-driven animation until their state and allocation semantics are explicit.
- Prefer compile-time constant folding, dead-branch elimination, and unused-state pruning over runtime helpers. Follow native-toolchain guidance: keep generated Swift/Kotlin direct, measure platform-level improvements, and do not claim speedups without generated-output or runtime evidence.
- Keep `Layout.isRegularWidth` as a typed responsive predicate with feature-gated native environment access: Swift horizontal size class and Compose configuration width `>= 600dp`. Document the platform-specific meaning and keep the broader breakpoint/device-class API on the roadmap until implemented.
- Keep `StatusBar` as one static configuration per native destination: app root or named screen. Lower `style` and `hidden` directly to SwiftUI/native Android status-bar APIs, remove the declaration before body generation, and reject nested or repeated declarations within one destination; keep background and animated transitions out until their cross-platform semantics are defined.
- Keep `BottomSheet` as a typed mutable Boolean binding with one native content tree. Lower to SwiftUI `.sheet` and Compose Material 3 `ModalBottomSheet`; do not add a cross-platform sheet manager or duplicate content, and defer snap-point/animation APIs until their native semantics are defined.
- Keep `RefreshControl` as a typed mutable Boolean binding plus direct actions. Lower to SwiftUI `.refreshable` and Compose Material 3 `PullToRefreshBox`; reuse the existing action lowering and do not implement custom scrolling physics or a refresh event bus.
- Keep `AppBottomBar` as a typed mutable `Int32` selection with static, unique non-negative tab indexes and labels. Lower to SwiftUI `TabView(selection:)` and Compose Material 3 `Scaffold`/`NavigationBar`; generate each tab body once, keep selection as ordinary native state, and defer icons, badges, and custom transitions until their cross-platform semantics are defined.
- Keep `Link(url: ...)` typed as a `String` expression. Validate literal URL schemes during semantic lowering, guard dynamic values with native `URL(string:)`/`Uri.parse` handling, and lower iOS to SwiftUI `Link` and Android to a direct `ACTION_VIEW` intent with handler checking. Keep incoming links, universal-link routing, and dynamic URL availability out of the IR until their compile-time and lifecycle semantics are defined.
- Keep `Accessibility(label: ..., role: ...)` as a typed semantics wrapper. Lower `String` label expressions and roles directly to Swift accessibility modifiers and Compose semantics; map Android headings with `heading()` and do not invent a shared accessibility runtime. Defer hints, focus actions, and richer dynamic values until their native lifecycle behavior is defined.
- Keep `Direction(value: LTR|RTL)` as a single static app-level configuration. Lower it to SwiftUI's `layoutDirection` environment and Compose's `LocalLayoutDirection`; preserve native leading/trailing and start/end mirroring and defer dynamic locale changes until lifecycle semantics are defined.
- Keep `OnAppear { ... }` and `OnDisappear { ... }` as one top-level callback of each app body or named screen, with direct assignment/`if` actions. Lower them to SwiftUI lifecycle modifiers and Compose `LaunchedEffect(Unit)`/`DisposableEffect(Unit)`; do not add a shared lifecycle registry or runtime event bus. Reject nested/repeated declarations until broader app lifecycle semantics are defined.
- `async fn` and `await` are a native-only async boundary: accept direct awaited app-local calls, require every async call to be awaited, and reject awaits outside async functions or `OnAppear async` blocks. Lower Swift to `async` plus `.task` and Kotlin to `suspend` plus `LaunchedEffect(Unit)`; do not add a scheduler, callback registry, or boxed future type.
- Function locals use ordered immutable `let` bindings. Resolve their types before native generation, reject duplicate/shadowed names, fold pure initializers, and remove unused pure locals without removing async work with observable effects. Emit direct Swift `let` and Kotlin `val` statements; do not add a local-variable runtime or boxed environment.
- Keep `Button` loading and disabled state as optional typed Booleans. Lower loading to a native `ProgressView`/`CircularProgressIndicator` branch and combine loading with `disabled` into one native enabled/disabled expression; omit each option's code when it is absent or statically false.
- Keep `Pressable` action blocks in the shared IR. The optional third block is long-press behavior: lower it to SwiftUI `.onLongPressGesture` and use Compose `combinedClickable` only when it is present; preserve the smaller `clickable` path for tap-only pressables. Keep pressed state, hover, focus, haptics, and custom accessibility actions out until their cross-platform semantics are defined.
- Keep `TextInput` submit actions in the shared IR. Lower the optional action block directly to SwiftUI `.onSubmit` and Compose `KeyboardActions`/`ImeAction.Done`; feature-gate those imports and modifiers so fields without submit behavior remain minimal. Keep focus, selection, autofill, password-manager integration, and validation out until their native semantics are defined.
- Preserve FastList as the public component name. Do not reintroduce the former UltraFastList name.

## Change workflow

1. Trace the feature from lexer/parser through semantic checks and IR into each affected backend.
2. Keep diagnostics source-aware and reject unsupported or ill-typed syntax before code generation.
3. Update focused language docs and examples when changing user-visible syntax or component behavior.
4. Run the narrowest relevant compiler/build checks. Inspect generated Swift/Kotlin for platform correctness; a successful Rust build alone does not prove generated native code compiles in a host app.
5. Avoid adding dependencies or runtime layers unless the feature requires them and their cost is clear.
